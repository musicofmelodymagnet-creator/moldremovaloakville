# Правила работы над сайтом moldremovaloakville.ca

## Проект и стек
- Информационный сайт под rank & rent: «Mold Removal Oakville» (удаление плесени, Oakville, ON). Контент — только текст и фото.
- **Astro 7 + Tailwind CSS v4** (`@tailwindcss/vite`), шрифты Inter / Manrope через `@fontsource-variable`.
- Сайт собирается локально на Mac в `dist/`, на сервер уходит только готовый статический HTML/CSS/JS. Node на сервере нет и не нужен.
- Форма заявки — маленький PHP-скрипт (`public/send.php`), PHP 8.3 на сервере есть.
- Команды:
  - `npm run dev` — локальный сервер (в фоне: `npx astro dev --background`, управление: `astro dev stop | status | logs`)
  - `npm run build` — сборка в `dist/`
  - `npm run preview` — просмотр собранной версии
  - `npm run deploy` — собрать, выложить на сервер и проверить (`-- --dry-run` — только показать, что будет загружено)
  - `npm run qa` — сборка + проверка главной по чек-листу ТЗ (H1, мета, OG, JSON-LD, FAQ = схема, якоря, плейсхолдеры в production)
  - `npm run check` — проверка типов Astro; `npm run brand` — пересоздать фавиконки, logo.png и og-image.png
  - `node scripts/qa/screens.mjs <папка>` — скриншоты desktop + iPhone и ошибки консоли
- Где что лежит:
  - `src/data/site.ts` — бизнес-данные: телефон, email, NAP, sameAs, GA4, цифры достижений, цены, отзывы, будущие URL услуг
  - `src/data/home.ts` — финальный текст главной ДОСЛОВНО из ТЗ (не переписывать, не сокращать — SEO-фразы расставлены намеренно)
  - `src/layouts/Layout.astro` — общий шаблон страницы (head, SEO-теги, JSON-LD, шапка, футер)
  - `src/components/` — общие блоки (см. раздел 6)
  - `src/styles/global.css` — Tailwind, цвета и шрифты (`@theme`), общие классы (`.btn-primary`, `.card`, `.eyebrow`)
  - `src/pages/` — страницы

## NO FAKE DATA — как устроены неподтверждённые данные
- Значение `null` в `src/data/site.ts` = данных нет. В dev (`npm run dev`) вместо него виден жёлтый плейсхолдер `[PHONE NUMBER]`, `[XX]+`, «VERIFY BEFORE PUBLISHING». В production-сборке такие элементы **не выводятся вообще** (флаг `SHOW_DRAFT`; посмотреть плейсхолдеры в сборке: `PUBLIC_SHOW_DRAFT=true npm run build`).
- Никогда не выдумывать: отзывы, рейтинг, число клиентов, годы опыта, сертификаты, сумму страховки, гарантию, адрес, телефон, email, членство в ассоциациях. Не добавлять `AggregateRating`/`Review` в схему, не ставить адрес/geo без реального NAP.
- Ссылки на будущие страницы услуг — в `servicePages` (`exists: false` → ссылка не выводится). Создал страницу → поставить `exists: true`, ссылки появятся в карточке и футере автоматически.
- Фото: компонент `Photo.astro` — без `image` рисует серую заглушку того же размера (без CLS). Реальные фото класть в `src/assets/` и передавать `image`.
- Форма: `public/send.php` (валидация, honeypot, rate limit, честные ошибки). Получатель — в `send-config.php` **только на сервере** (шаблон `scripts/send-config.example.php`). Пока его нет, форма честно отвечает «временно недоступно», а не фальшивым успехом. GA4 `generate_lead` — только после реального успеха (нужен `ga4Id` в site.ts).

## 2. Git и коммиты
- Коммитить только когда явно попросили, но **после каждого коммита сразу делать `git push`**, без дополнительного запроса.
- Репозиторий публичный: перед коммитом смотреть `git status` / `git diff --cached` и убеждаться, что `.deploy.env`, пароли и другие секреты не попали в коммит.

- Не использовать `--no-verify`, `--amend` на уже запушенных коммитах без явной просьбы.

## 3. Деплой на сервер — методология
- **Выкладка одной командой: `npm run deploy`** (скрипт `scripts/deploy.sh`). Делает 4 шага: сборка → rsync `dist/` на сервер → сверка контрольных сумм md5 каждого файла на сервере с `dist/` → проверка живого сайта с сервера (коды 200 для `/`, `/sitemap.xml`, `/robots.txt` и что главная отдаёт новую версию). «Задеплоено» говорить только если скрипт закончил строкой `✓ Задеплоено и проверено`.
- **`npm run deploy -- --dry-run`** — пробный режим: собирает и показывает список файлов, которые будут загружены, на сервере ничего не меняет.
- Пароль в скрипт подставляет `scripts/lib/with-pass.exp` из переменной окружения (берёт из `.deploy.env`), в аргументах процесса и в git пароля нет.
- На macOS встроенный rsync старый (2.6.9): права задаются как `--chmod=Du=rwx,Dgo=rx,Fu=rw,Fgo=r`, запись `D755,F644` он не понимает.
- Порядок внутри скрипта: `npm run build` → выкладка **всей папки `dist/` через `rsync` без `--delete`** (новые и изменённые файлы загружаются, лишние файлы на сервере не удаляются).
- Вход по паролю — через `expect`. Пароль и адрес брать из `.deploy.env` (`source .deploy.env`), **не вписывать их в скрипты, которые попадают в git**. Не спрашивать пароль заново каждый раз. Шаблон:
  ```
  source .deploy.env
  expect <<EOF
  set timeout 120
  spawn rsync -az -e "ssh -p $DEPLOY_PORT" dist/ $DEPLOY_USER@$DEPLOY_HOST:$DEPLOY_PATH/
  expect { -re "(?i)password:" { send "$DEPLOY_PASS\r"; exp_continue } eof }
  EOF
  ```
- **Всегда использовать полный абсолютный путь** на сервере (`/home/admin/web/moldremovaloakville.ca/public_html/...`), а не сокращённый `public_html/...` — относительный путь от домашней папки SSH-пользователя может вести не туда, где реально находится DocumentRoot.
- Перед деплоем — выяснить и задокументировать (в памяти) реальную карту путей: как локальная структура соотносится с путями на сервере (особенно если есть redirect/rewrite, из-за которых красивый URL физически лежит в другой папке).
- **Обязательная проверка после каждого деплоя**: никогда не считать файлы выложенными по сообщению «done» от скрипта — expect может закончиться «успешно», даже если rsync/scp тихо не сработал (таймаут, неверный путь). Всегда проверять реальное содержимое на сервере отдельной командой (`ssh … ls/grep/cat`) и живой сайт (`curl -sI https://moldremovaloakville.ca/...`), и только после этого говорить «задеплоено».
- Кэш: CSS/JS, которые собирает Astro (`/_astro/...`), получают хэш в имени автоматически — `?v=N` для них не нужен. Для файлов из `public/` (картинки, видео), перезаливаемых под тем же именем, учитывать прокси-кэш (nginx): проверять заголовки `Content-Length` / `ETag` и при необходимости версионировать через `?v=N` в ссылке.
- HTML-страницы должны отдаваться без долгого кэша (`Cache-Control: no-cache`), статика (css/js/шрифты/картинки) — с долгим кэшем.

## 4. SEO / технический чек-лист при любых изменениях страниц
После любой правки контента страницы проверять и поддерживать в порядке:
- SEO Title, Meta Description, единственный `<h1>` на странице.
- `canonical` указывает на правильный итоговый URL.
- JSON-LD структурированные данные: одинаковое название бренда/организации/сайта во ВСЕХ узлах (`LocalBusiness`/`HomeAndConstructionBusiness`, `Organization`, `WebSite`, `Service.provider` и т.д.) — расхождения мешают Google уверенно определить название сайта для сниппета.
- Видимый текст FAQ и `FAQPage` JSON-LD `"text"` должны **дословно совпадать** (включая цены и условия — меняешь одно, меняй оба). В проекте оба берутся из `faq` в `src/data/site.ts` — не разводить их.
- `sitemap.xml` — у любой изменённой страницы (текст, картинка, шрифт, CSS-эффект, а не только у новых страниц) обязательно обновлять `<lastmod>` на дату правки. **В проекте это автоматически**: интеграция `integrations/sitemap-lastmod.mjs` после каждой сборки считает хэш итогового HTML каждой страницы; если он изменился — ставит сегодняшнюю дату (по Торонто), если нет — оставляет прежнюю. Хэши и даты хранятся в `src/data/sitemap-state.json` — **этот файл коммитить вместе с правками**, иначе даты потеряются. Руками `lastmod` не править. В карту не попадают `404.html` и страницы с `<meta name="robots" content="noindex">` (так прятать страницу «спасибо»).
- `robots.txt` лежит в `public/robots.txt` и выкладывается вместе с сайтом (перезаписывает серверный).
- После деплоя — пинговать поисковики о новом контенте: IndexNow (Bing/Yandex) и Google Search Console (перечитать sitemap), когда для проекта будут настроены такие скрипты/API.
- `robots.txt` — закрывать служебные пути, которые не должны индексироваться как отдельные страницы: `/send.php`, `/api/` (если появится), страницу «спасибо за заявку».
- Периодически (или по сигналу пользователя со скриншотом GSC) — открывать Google Search Console → «Why pages aren't indexed» / Coverage и разбирать КАЖДЫЙ URL реальной проверкой на живом сайте (`curl -sI` через SSH с сервера, а не из песочницы — исходящий интернет из sandbox может быть заблокирован), а не полагаться на данные GSC вслепую (они кэшируются и могут отставать на недели).
- «Page with redirect» и «Alternate page with proper canonical tag» — это НЕ ошибки сами по себе, а ожидаемое поведение для неканонических вариантов URL (www/non-www, http/https, `/index.html`, старые слаги). Паниковать не нужно, если редирект/canonical настроен правильно.
- Реальная проблема — если служебный фрагмент индексируется как отдельная страница, дубликаты без canonical, настоящий redirect loop или 4xx на странице, которая должна быть живой.
- Редиректы для старых URL — по возможности в один переход (не двухшаговый www-strip → потом редирект старого слага). Более специфичные правила (конкретный старый слаг) ставить раньше общих и сразу вести на абсолютный финальный `https://moldremovaloakville.ca/...` URL.

## 8. Технические ловушки, которые уже всплывали
- **Инлайн критический CSS**: если CSS инлайнится в `<head>` (Astro делает это сам для небольших стилей), следить, чтобы `@media`/`@supports`-правила были корректно закрыты — проверять через `PerformanceObserver` layout-shift в браузере, а не только на глаз по скриншоту.
- **Кэш прокси на статике**: перезалив файла «на том же месте» может отдавать старые байты из прокси-кэша (nginx) — версионировать через `?v=N` (для файлов из `public/`).
- **CSP (Content-Security-Policy)**: любой новый сторонний скрипт (аналитика, виджеты, шрифты) нужно добавить в allowlist CSP в конфиге сервера, если CSP включён, иначе браузер тихо его заблокирует без явной ошибки в интерфейсе.
- **HTML и кэш**: сервер может переопределять `no-cache` для `.html` более общим правилом (например, длинным `max-age` в nginx) — проверять реальную отдачу через `fetch(url, {cache: 'no-store'})` / `curl -sI`, а не обычной навигацией браузера.
- **Права на запись на сервере**: некоторые SSH-пользователи не могут создавать НОВЫЕ файлы в корне docroot (ACL), но могут в подпапках. Не считать это блокером — проверять через `ls` после выкладки. (Для этого проекта запись в корень `public_html` проверена и работает.)
- **Вложенные HTML-комментарии**: перед тем как обернуть уже закомментированный блок в новый внешний `<!-- -->`, убрать внутренние маркеры комментариев, иначе разметка ломается.
- **Мобильное тестирование**: проверять не только стандартные 375–428px, но и узкие 280–340px (масштабирование «Display size» на Android) — специфичные баги часто всплывают именно там. Проверять плагином Playwright. Для свайп-каруселей использовать `touch-action: pan-y`, а не `manipulation`.
- **Измерение текста через JS**: если измеряешь естественную ширину многострочного текста с принудительным переносом — измерять КАЖДУЮ строку отдельно с `white-space: nowrap` и только после `document.fonts.ready`, иначе замер упрётся в ширину экрана и даст неверный результат.

## 9. Аккуратность с рискованными действиями
- Не выполнять деструктивные операции (удаление файлов/веток, `rm -rf`, перезапись без бэкапа, force push, `rsync --delete`) без явного запроса пользователя на каждый конкретный случай — одно разрешение не значит разрешение навсегда.
- Перед любой командой, способной стереть незакоммиченные изменения, — сначала `git status`.
- При staging/commit — смотреть, что реально попало в коммит (`git status` / `git diff`), особенно на предмет секретов (`.deploy.env`, `.env`, пароли).
- Публикация чего-либо во внешние сервисы — только после явного согласия пользователя, с пониманием, что это может быть проиндексировано/закэшировано третьими лицами даже после удаления.

## 10. Память между сессиями
- Вести 4 типа памяти: **user** (кто пользователь, роль, опыт), **feedback** (что подтвердилось / что поправили — с «почему»), **project** (текущие задачи, дедлайны, решения), **reference** (внешние системы: где искать баги, аналитику, доступы).
- Не дублировать в память то, что можно достать из кода или git-истории — только то, что не восстановить чтением репозитория.
- Обновлять/удалять память, если она устарела или оказалась неверной. Не действовать по памяти вслепую — перед использованием сверяться с текущим состоянием файлов/сервера.
